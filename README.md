# مطعم أبو كريم الحاتي — موقع + سيرفر حسابات مستقل

```
abu-karim-project/
├── web/                    ← الموقع (يُنشر على Vercel)
│   ├── index.html          ← نفس موقعك بعد استبدال Firebase بالسيرفر الجديد
│   ├── config.js           ← عنوان السيرفر (يُولَّد تلقائيًا على Vercel من API_BASE_URL)
│   ├── build-config.js     ← سكربت البناء الذي يكتب config.js
│   └── vercel.json
├── server/                 ← السيرفر المستقل (يُنشر على Render)
│   ├── src/                ← كود Express
│   ├── schema.sql          ← جدول الحسابات (users) فقط
│   ├── .env.example
│   ├── package.json
│   └── test/auth.test.js   ← اختبار تكاملي (يحتاج قاعدة بيانات اختبار)
└── render.yaml             ← إعداد Render الجاهز (اختياري)
```

## كيف يعمل النظام
- الموقع (Vercel) يتصل بالسيرفر (Render) عبر `fetch` مع الكوكيز.
- السيرفر يحفظ الحسابات في Neon PostgreSQL: `id`، `name`، `email`، `password_hash` (bcrypt)، `created_at`.
- بعد الدخول يضع السيرفر كوكي `ak_session` من نوع **HttpOnly + Secure**، فلا يستطيع JavaScript قراءته، ويبقى محفوظًا بعد تحديث الصفحة وبعد إغلاق المتصفح (30 يومًا افتراضيًا).
- نقاط الـ API: `POST /api/auth/signup` ، `POST /api/auth/login` ، `POST /api/auth/logout` ، `GET /api/auth/me` ، `GET /health`.
- لوحة الإدارة وكلمة سرها (داخل الموقع نفسه) لم تُمسّ ولا علاقة لها بحسابات الزبائن.

---

## الخطوة 1: قاعدة البيانات (Neon)
1. أنشئ حسابًا على https://neon.tech ثم **Create project**.
2. من لوحة المشروع افتح **Connect** وانسخ **Connection string** (يشبه `postgresql://user:pass@ep-xxx.neon.tech/neondb?sslmode=require`). احتفظ به: هذا هو `DATABASE_URL`.
3. الجدول يُنشأ تلقائيًا عند تشغيل السيرفر أول مرة. (أو شغّل محتوى `server/schema.sql` يدويًا من **SQL Editor** في Neon.)

## الخطوة 2: ارفع المشروع إلى GitHub
أنشئ مستودعًا (Repository) خاصًا وارفع محتوى هذا المجلد كما هو. ملف `.gitignore` يمنع رفع `.env`.

## الخطوة 3: السيرفر على Render
1. في https://render.com اختر **New → Web Service** واربطه بمستودع GitHub.
2. الإعدادات:
   - **Root Directory:** `server`
   - **Build Command:** `npm install`
   - **Start Command:** `npm start`
   - **Health Check Path:** `/health`
3. أضف **Environment Variables**:

| المتغير | القيمة |
|---|---|
| `DATABASE_URL` | رابط Neon من الخطوة 1 |
| `SESSION_SECRET` | نص عشوائي طويل. ولّده بالأمر: `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"` |
| `CORS_ORIGINS` | رابط موقعك على Vercel بدون `/` في النهاية، مثل `https://abu-karim.vercel.app` (ضعه بعد الخطوة 4، أو ضع مؤقتًا أي رابط ثم عدّله) |
| `NODE_ENV` | `production` |

   (بديل أسهل: **New → Blueprint** وسيقرأ `render.yaml` ويطلب منك `DATABASE_URL` و`CORS_ORIGINS` فقط.)
4. بعد النشر انسخ رابط الخدمة، مثل `https://abu-karim-auth.onrender.com`، وافتح `رابطك/health` — يجب أن ترى `{"ok":true}`.

## الخطوة 4: الموقع على Vercel
1. في https://vercel.com اختر **Add New → Project** واستورد نفس المستودع.
2. **Root Directory:** `web` ، و**Framework Preset:** Other (الباقي يأتي من `vercel.json`).
3. أضف متغير البيئة: `API_BASE_URL` = رابط سيرفر Render (بدون `/` في النهاية).
4. اضغط **Deploy**. سكربت البناء يكتب `config.js` تلقائيًا. إذا نسيت المتغير يفشل البناء برسالة واضحة.
5. ارجع إلى Render وتأكد أن `CORS_ORIGINS` يطابق رابط Vercel تمامًا (بما في ذلك `https://`). إن استخدمت دومينًا خاصًا أضفه أيضًا مفصولًا بفاصلة.

## التشغيل المحلي للتجربة
```bash
cd server
cp .env.example .env      # عدّل DATABASE_URL و SESSION_SECRET و CORS_ORIGINS=http://localhost:8080
                          # وضع NODE_ENV=development و DATABASE_SSL=false لو القاعدة محلية بدون SSL
npm install
npm start                 # السيرفر على http://localhost:3000

# في نافذة أخرى:
cd web && python3 -m http.server 8080    # ثم افتح http://localhost:8080
```
`web/config.js` الافتراضي يشير إلى `http://localhost:3000`.

## ⚠️ ملاحظات مهمة

**1) الكوكيز بين دومينين مختلفين.** الموقع على `vercel.app` والسيرفر على `onrender.com` يُعتبران موقعين مختلفين، لذلك الكوكي يُرسل بالوضع `SameSite=None; Secure`. معظم المتصفحات تقبله، لكن **Safari (آيفون/ماك) وبعض المتصفحات المتشددة تحظر كوكيز الطرف الثالث**، وقد لا تبقى الجلسة فيها. الحل الدائم والموصى به: استخدم دومينًا خاصًا للموقع والسيرفر تحت نفس الدومين الرئيسي، مثل `www.example.com` للموقع و`api.example.com` للسيرفر، ثم اضبط على Render:
`COOKIE_SAMESITE=lax` و `COOKIE_DOMAIN=.example.com` وعدّل `CORS_ORIGINS` و`API_BASE_URL` إلى الدومينات الجديدة.

**2) الاستضافة المجانية على Render تنام** بعد فترة خمول، وأول طلب بعدها قد يأخذ ~30–50 ثانية. الموقع يتحمل ذلك (مهلة 70 ثانية) لكن أول دخول قد يتأخر.

**3) تغييرات عن النسخة القديمة:**
- الحد الأدنى لكلمة المرور صار **8 أحرف** (كان 6) وتم تعديل النص في النموذج.
- حُذف زر «نسيت كلمة المرور؟» لأنه كان يعتمد على بريد Firebase؛ استعادة كلمة المرور تحتاج خدمة إرسال بريد (SMTP) ولم تكن ضمن المطلوب. إن أردتها لاحقًا تُضاف كخطوة مستقلة.
- حسابات Firebase القديمة **لا تُنقل تلقائيًا** (كلمات مرورها مشفرة داخل Firebase). يحتاج أصحابها إلى إنشاء حساب جديد.
- كود Firebase ومفاتيحه حُذفت بالكامل من `index.html`.

**4) تسجيل الخروج** يمسح الكوكي من المتصفح. الجلسة عبارة عن توقيع مشفر (JWT) بدون جدول جلسات في قاعدة البيانات (لأن القاعدة مخصصة للحسابات فقط)، فلو سُرق الكوكي قبل الخروج يبقى صالحًا حتى انتهاء مدته. لإبطال كل الجلسات فورًا غيّر `SESSION_SECRET`.

## الحماية المطبّقة
- كلمات المرور بـ bcrypt (12 جولة)، ولا تُحفظ ولا تُسجَّل كنص عادي.
- كل التحقق (البريد، الاسم، كلمة المرور) يتم في السيرفر أيضًا.
- منع تكرار البريد في قاعدة البيانات (فهرس فريد بدون حساسية لحالة الأحرف).
- حماية من التخمين: حد لكل IP (30 محاولة/15 دقيقة) وحد لكل بريد (8 محاولات فاشلة/15 دقيقة).
- رسالة موحدة لخطأ الدخول (لا تكشف هل البريد موجود)، ومقارنة زمنية متساوية.
- CORS لموقعك فقط + رفض طلبات التعديل القادمة من أي Origin آخر (حماية CSRF).
- ترويسات `helmet`، وحد حجم الطلب 10KB.
- الاستجابات تُرجع `id` و`name` فقط، لا بريد ولا هاش.
- كل الأسرار في متغيرات البيئة، ولا شيء منها داخل ملفات الموقع.

## ما تم اختباره وما لم يُختبر (بصدق)
**اختُبر فعليًا** (متصفح Chromium حقيقي على `index.html` المعدّل، مع سيرفر تجريبي بسيط يطبّق نفس عقد الـ API): فتح الصفحة بلا أخطاء، عدم وجود تمرير أفقي على الموبايل، رسائل التحقق، إنشاء حساب، عرض الاسم، الكوكي HttpOnly، بقاء الجلسة بعد التحديث وبعد إغلاق المتصفح وفتحه، تسجيل الخروج، رسالة البريد المكرر، دخول خاطئ وصحيح، وسلوك الواجهة عند تعطل السيرفر. كذلك نقر كل أزرار الموقع على الموبايل والكمبيوتر دون أي خطأ جافاسكربت (نفس النتيجة للنسخة الأصلية)، وفحص صيغة (syntax) كل ملفات السيرفر واختبار وحدة التحقق من البيانات.

**لم يُشغَّل هنا:** كود السيرفر الحقيقي مع Express وPostgreSQL وbcrypt، لأن بيئة التطوير التي أُعدّ فيها المشروع بلا إنترنت فلم يمكن تثبيت الحزم ولا تشغيل قاعدة بيانات. لذلك لم يُختبر فعليًا: الحفظ في Neon، وتشفير bcrypt، وحدود المحاولات، وCORS الفعلي، والنشر على Render وVercel. جهّزتُ لك اختبارًا يغطي ذلك كله، شغّله مرة واحدة على قاعدة بيانات **اختبار** (ليست قاعدة الإنتاج) قبل الاعتماد على النظام:
```bash
cd server && npm install
TEST_DATABASE_URL="postgresql://..." npm test
```
يغطي: إنشاء الحساب، bcrypt في القاعدة، البريد المكرر، التحقق، الجلسة والخروج، الدخول الصحيح والخاطئ، رفض الـ Origin الغريب، وحد المحاولات. وإن ظهر أي خطأ أرسله لي وأصلحه.
